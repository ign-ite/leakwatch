# Leakwatch

Finds money leaking out of accounts payable: invoices paid twice, invoices billed above the contract
price, and contract terms (price cuts, volume rebates) that were agreed by email but never applied.

Who it's for: finance and accounts-payable teams that want to find recoverable money in their ERP exports.

**Live app:** _link added after deploy_

## Invoice leakage (`leakage/`)

Three ERP exports, each with its own formats (European dates and decimals, uppercase vendor names
with `PVT LTD`, `(India) Private Limited` variants and typos), are:

1. **Cleaned** into one table with pandas: dates and numbers parsed, vendor names matched to a
   master list (exact after normalizing, then fuzzy with `difflib`; weak matches are marked for review
   and names that match nothing are excluded and counted),
   and OCR misreads in invoice numbers undone (`O→0`, `I→1`, `S→5`, leading zeros).
2. **Checked** with three SQL rules in SQLite (`leakage/sql/`, commented step by step):
   - exact duplicates: `ROW_NUMBER()` over vendor + invoice number + amount
   - OCR duplicates: `LAG()` to the previous payment with the same cleaned number, within 30 days
   - price overcharges: `JOIN` to the contract price list
   Duplicates already reversed by a credit note are excluded.
3. **Ranked** by priority = recoverable value × confidence, and summarized in a downloadable audit memo.

The data is synthetic (`leakage/generate.py`, fixed seed) with planted problems recorded in an
answer key, so every rule has a measured precision and recall. It also plants legitimate payments that
look like leakage: duplicates already reversed by a credit note, recurring same-amount invoices, a
vendor reusing an invoice number a year later, and look-alike numbers (`O/0`, `I/1`, `S/5`, a leading zero). The first
two are ignored; the last two are flagged, which is why exact and OCR precision are about 0.93–0.94
rather than 1.0. The app shows why each planted problem was missed.

## Contract terms (`contracts/`)

Thirty rate contracts and ten supplier emails (`data/documents/`, generated by
`contracts/generate_contracts.py`) state prices, lower them from a date, or offer volume rebates.
They are written the way real documents vary: `₹`, `Rs.`, `INR` and "rupees"; day-first dates like
`01/08/2025`; `108k units`; email threads that quote the *old* price; and percentages (freight
surcharges, late-payment interest) that are not rebates.

1. **Extracted** with Gemini as schema-validated JSON (`contracts/extract.py`). Each term must carry
   a quote that appears verbatim in the document; terms whose quote can't be found, with low
   confidence, or with an unknown vendor or item go to a review queue instead of being used.
   API errors and invalid output are retried once, then the document is reported as failed.
2. **Scored** field by field against an answer key (`contracts/evaluate.py`), listing every wrong
   field, missed term and extra (hallucinated) term, with tokens and latency per document.
3. **Checked** against the invoices from the first part (`contracts/compliance.py`): invoices billed
   above a lowered price (only the part the first part can't see) and rebates whose volume was
   reached but never credited. The same checks run on the true terms, so the cost of extraction
   errors shows in rupees.

Extraction runs once, offline, and saves `contracts/extractions.json`; the app reads that file, so
it needs no API key, and the contract tab appears once the file exists. To run it: put
`GEMINI_API_KEY = "..."` in `.streamlit/secrets.toml` and run `uv run python -m contracts.extract`.

## Run it

```bash
uv sync
uv run streamlit run app.py
uv run pytest
```

Regenerate the data with `uv run python -m leakage.generate`, then
`uv run python -m contracts.generate_contracts`.

## Limitations

- Synthetic data is cleaner than real AP data.
- No multi-currency invoices or partial payments.
- Confidence scores are hand-set, not learned. The model's self-reported confidence is
  uncalibrated and rarely low, so the evidence checks do most of the filtering.
- The evidence check proves the quote is in the document (not in a quoted earlier message) and
  that the price or rebate % is written in it; it can't prove dates or quantities came from it.
- Documents are generated from templates, so they are tidier than scanned contracts.
- Exact matches have no time limit, so a reused invoice number a year later is flagged.
